# MATLAB-to-AIE: Graph

Generate the AI Engine graph definition, application wrapper, compiler configuration, and build system.

---

## Prerequisites

- Kernel `.h` and `.cpp` files have been generated by `matlab-to-aie-kernel`
- Analysis report is available (dimensions, port count, buffer sizes)
- User has specified (or will be asked): PLIO vs GMIO, platform target
- **Target board/part has been determined by the parent skill** (e.g., `xcvc1902-vsva2197-2MP-e-S` for VCK190)

---

## Workflow

### Step 1: Determine I/O Style

Ask the user if not already specified: **"Should the kernel use PLIO (PL-to-AIE streaming) or GMIO (Global Memory I/O) ports?"**

| I/O Style | When to Use | Characteristics |
|---|---|---|
| PLIO | Streaming data from PL fabric or Test Harness | 32/64/128-bit interface, deterministic timing |
| GMIO | Large data transfers from DDR | Burst transfers via shim DMA, higher bandwidth for bulk data |

**Default recommendation**: PLIO for designs that will use Test Harness or connect to PL kernels; GMIO for standalone testing of compute-heavy kernels with large matrices.

### Step 2: Generate Graph Header (KERNEL_graph.h)

**This must follow the `create-kernel-graph` foundational skill pattern.**

The graph header is named `<kernel_name>_graph.h` (not `graph.h`).

```cpp
// <kernel_name>_graph.h
// AI Engine graph definition for <kernel_name>
//
// Copyright (C) <year>, Advanced Micro Devices, Inc. All rights reserved.
// SPDX-License-Identifier: MIT

#pragma once
#include <adf.h>
#include "<kernel_name>.h"
using namespace adf;

class KernelName_graph : public graph {
private:
    kernel kk;
public:
    // Graph ports (one per kernel port)
    input_port  in_A;
    input_port  in_B;
    output_port out_C;

    KernelName_graph(void)
    {
        kk = kernel::create_object<KernelName>();
        source(kk) = "<kernel_name>.cpp";
        runtime<ratio>(kk) = 0.9;

        // Connect graph ports to kernel ports
        connect<>(in_A, kk.in[0]);
        connect<>(in_B, kk.in[1]);
        connect<>(kk.out[0], out_C);

        // Set buffer dimensions (# samples per invocation)
        dimensions(kk.in[0])  = { KernelName::NSAMP_IN_A };
        dimensions(kk.in[1])  = { KernelName::NSAMP_IN_B };
        dimensions(kk.out[0]) = { KernelName::NSAMP_OUT_C };
    }
};
```

**Key rules** (aligned to `create-kernel-graph`):
- File naming: `<kernel_name>_graph.h` (not `graph.h`)
- Include the kernel `.h` file (not `.hpp`)
- Use `kernel::create_object<KernelName>()` (no template params — they are now constexpr in class)
- Use `dimensions()` with the `NSAMP_*` constants from the kernel header
- Define separate `input_port`/`output_port` on the graph class (not PLIO/GMIO here — those belong in the app)
- `runtime<ratio>` = 0.9 for compute-intensive kernels
- Port numbering follows the order in the kernel `run()` signature

#### Registered Parameter Support (`optimize-aie-buffers-to-parameters`)

If the `matlab-to-aie-kernel` step applied the `optimize-aie-buffers-to-parameters`
optimization (large working arrays moved to class members with `REGISTER_PARAMETER`),
the graph must provide backing storage via `std::vector` passed to `kernel::create_object<>()`:

```cpp
class KernelName_graph : public graph {
private:
    kernel kk;
    // Backing vectors for registered parameters
    std::vector<cfloat> work_A_vec;
    std::vector<cfloat> work_B_vec;
public:
    input_port  in_A;
    output_port out_C;

    KernelName_graph(void)
        : work_A_vec(KernelName::BUF_A_SIZE),
          work_B_vec(KernelName::BUF_B_SIZE)
    {
        kk = kernel::create_object<KernelName>(work_A_vec, work_B_vec);
        source(kk) = "<kernel_name>.cpp";
        runtime<ratio>(kk) = 0.9;
        // ... port connections ...
    }
};
```

When registered parameters are used, the `.aiecst` constraints file can also specify
memory bank placement for the registered buffers to avoid bank conflicts:

```json
{
    "NodeConstraints": {
        "KernelName_graph.kk": {
            "parameters": {
                "work_A": { "bank": 0 },
                "work_B": { "bank": 2 }
            }
        }
    }
}
```

See skill `optimize-aie-buffers-to-parameters` for the full pattern.

### Step 3: Generate Graph Application (KERNEL_app.cpp)

**This must follow the `create-kernel-app` foundational skill pattern.**

The app file is named `<kernel_name>_app.cpp` and uses a `dummy_graph` wrapper that creates
the top-level I/O ports (PLIO or GMIO) and connects them to the kernel graph.

```cpp
// <kernel_name>_app.cpp
// AI Engine graph application for simulation
//
// Copyright (C) <year>, Advanced Micro Devices, Inc. All rights reserved.
// SPDX-License-Identifier: MIT

#include "<kernel_name>_graph.h"

class dummy_graph : public graph {
public:
    input_plio  in_A;
    input_plio  in_B;
    output_plio out_C;
    KernelName_graph dut;

    dummy_graph(void) {
        in_A  = input_plio::create("PLIO_in_A",  plio_128_bits, "data/input_A.txt");
        in_B  = input_plio::create("PLIO_in_B",  plio_128_bits, "data/input_B.txt");
        out_C = output_plio::create("PLIO_out_C", plio_128_bits, "data/output_C.txt");

        connect<>(in_A.out[0],  dut.in_A);
        connect<>(in_B.out[0],  dut.in_B);
        connect<>(dut.out_C, out_C.in[0]);
    }
};

dummy_graph mygraph;

int main(void)
{
    mygraph.init();
    mygraph.run(NUM_ITERATIONS);  // Number of kernel invocations
    mygraph.end();
    return 0;
}
```

**GMIO variant** (replace PLIO declarations):
```cpp
    input_gmio  in_A;
    input_gmio  in_B;
    output_gmio out_C;
    ...
    in_A  = input_gmio::create("GMIO_in_A",  64, 5000);
    in_B  = input_gmio::create("GMIO_in_B",  64, 5000);
    out_C = output_gmio::create("GMIO_out_C", 64, 5000);
```

**Key rules** (aligned to `create-kernel-app`):
- File naming: `<kernel_name>_app.cpp`
- The `dummy_graph` wrapper owns the external I/O ports (PLIO/GMIO) and connects them to the kernel graph
- The kernel graph class (`KernelName_graph`) uses generic `input_port`/`output_port` — NOT PLIO/GMIO directly
- This separation allows the same kernel graph to be reused with different I/O configurations
- `NUM_ITERATIONS` = number of kernel invocations for the full computation
- `mygraph` must be a global object (not inside main)
- PLIO width recommendation: `plio_128_bits` for maximum bandwidth
- PLIO data files placed in `data/` directory
### Step 4: Generate AIE Compiler Configuration (aie.cfg)

**This must follow the `create-kernel-cfg` foundational skill pattern.**

```ini
[aie]
kernel-linting=true
xlopt=1
verbose=true
pl-freq=625
Xmapper=BufferOptLevel9
#stacksize=2048
#Xchess="main:backend.mist2.maxfoldk=500"
```

**IMPORTANT**:
- Use the template from `create-kernel-cfg` as-is — it includes `kernel-linting=true` for compile-time port checking, `verbose=true` for detailed scheduling logs, and `Xmapper=BufferOptLevel9` for optimal buffer placement.
- Do NOT include `part=` in aie.cfg — it causes `unrecognised option 'aie.part'` error. The part is specified via `--part` on the `v++` command line in the Makefile.
- Do NOT include `workdir=` in aie.cfg — the work directory is managed by `v++` automatically.
- The `[aie]` INI-style format is interpreted by `v++ --config`. Do NOT use this file directly with `aiecompiler --config`.
- `pl-freq=625` sets PL clock frequency for PLIO interfaces (adjust if needed).
- Uncomment `stacksize` only if the kernel requires a larger stack (recursive calls, large locals).
- Uncomment `Xchess` to customize backend folding limits for modulo scheduling.

### Step 5: Generate Makefile

**This must follow the `create-kernel-makefile` foundational skill pattern.**

**Architecture-specific `part` values** (specified in Makefile as `PART_USE` variable):

| Architecture | Part | Board |
|---|---|---|
| AIE | `xcvc1902-vsva2197-2MP-e-S` | VCK190 |
| AIE-ML | `xcve2802-vsvh1760-2MP-e-S` | VEK280 |
| AIE-ML v2 | `xcve3858-sfvc784-2MP-e-S` | VEK385 |

```makefile
# Makefile for AI Engine kernel: <kernel_name>
# Ported from MATLAB: <matlab_function_name>.m
#
# Copyright (C) <year>, Advanced Micro Devices, Inc. All rights reserved.
# SPDX-License-Identifier: MIT

SIM_FIFO          := false
MY_APP            := <kernel_name>_app
MY_SOURCES        := ${MY_APP}.cpp <kernel_name>_graph.h <kernel_name>.h <kernel_name>.cpp
PART_USE          := <part_name>
CHECK_FIFO        := --aie.evaluate-fifo-depth --aie.Xrouter=disablePathBalancing
DSPLIB_OPTS       := --include=${DSPLIB_ROOT}/L2/include/aie \
                     --include=${DSPLIB_ROOT}/L1/include/aie \
                     --include=${DSPLIB_ROOT}/L1/src/aie
AIE_OUTPUT := libadf.a
AIE_FLAGS :=    ${DSPLIB_OPTS} --part=${PART_USE} ${MY_APP}.cpp --aie.output-archive=${AIE_OUTPUT}
AIE_FLAGS :=    ${AIE_FLAGS} --aie.constraints=${MY_APP}.aiecst
AIE_SIM_FLAGS :=    --hang-detect-time=500000 --display-run-interval=1000

ifeq (${SIM_FIFO}, true)
	AIE_FLAGS := ${AIE_FLAGS} ${CHECK_FIFO}
endif

.PHONY: all clean x86com x86sim sim profile throughput

all:		${AIE_OUTPUT}

${AIE_OUTPUT}:	${MY_SOURCES}
	v++ --compile --config aie.cfg --mode aie --target=hw ${AIE_FLAGS} |& tee log

x86com:
	v++ --compile --config aie.cfg --mode aie --target=x86sim ${AIE_FLAGS} |& tee log

sim:
	aiesimulator ${AIE_SIM_FLAGS} |& tee -a log

x86sim:
	x86simulator |& tee -a log

profile:
	aiesimulator ${AIE_SIM_FLAGS} --online -wdb -text --profile |& tee -a log

trace:
	aiesimulator ${AIE_SIM_FLAGS} --online -wdb -text |& tee -a log

clean:
	rm -rf log x86simulator_output aiesimulator_output .AIE_SIM_CMD_LINE_OPTIONS .Xil
	rm -rf Work ${AIE_OUTPUT} *.log *.wcfg *.wdb *.csv sol.db function_wdb_dir trdata.aiesim vfs_work
	rm -rf pl_sample_counts throughput_info.json .Xil ISS_RPC_SERVER_PORT
```

**Key rules** (aligned to `create-kernel-makefile`):
- Use `v++ --compile --config aie.cfg --mode aie` with flags built in `AIE_FLAGS`
- Specify `--part=${PART_USE}` in `AIE_FLAGS` — NOT in aie.cfg
- Default target (`all`) compiles for hw (cycle-accurate)
- `x86com` target for x86 compilation, `x86sim` for execution
- `sim` target for aiesimulator execution
- `profile` and `trace` targets for detailed analysis
- Include `DSPLIB_OPTS` for DSP library compatibility
- Include `--aie.constraints=${MY_APP}.aiecst` for floorplan constraints
- Include `--aie.output-archive=${AIE_OUTPUT}` for output artifact naming
- `SIM_FIFO` flag for optional FIFO depth evaluation

### Step 6: Generate Constraints File (KERNEL_app.aiecst)

**This must follow the `create-kernel-aiecst` foundational skill pattern.**

Create `<kernel_name>_app.aiecst` with empty JSON to allow future floorplanning:

```json
{}
```

This file is referenced by the Makefile via `--aie.constraints=${MY_APP}.aiecst`. It enables:
- Tile placement constraints for multi-kernel designs
- Buffer location constraints for optimized data movement
- Cascade chain constraints for pipeline architectures

### Step 7: Generate Test Data Directory Structure

Create the `data/` directory with placeholder input files:

```
data/
├── input_A.txt    ← Input matrix A (one element per line, space-separated for vectors)
├── input_B.txt    ← Input matrix B
└── golden_C.txt   ← Expected output (generated by MATLAB test harness)
```

**Data file format** (for PLIO):
- One sample per line
- Integer representation for fixed-point (raw integer value)
- Decimal representation for floating-point
- For complex: real and imaginary parts space-separated on same line

## Multi-Kernel Graphs

If the analysis report indicated a multi-kernel pipeline:

1. Instantiate multiple kernels in the graph
2. Connect intermediate buffers between kernels
3. Only expose external-facing ports as PLIO/GMIO
4. Consider cascade connections for tightly coupled kernels (reduces memory bandwidth)

```cpp
// Multi-kernel example
kernel k1, k2;
k1 = kernel::create_object<Stage1Kernel>();
k2 = kernel::create_object<Stage2Kernel>();

connect<>(in_A, k1.in[0]);
connect<>(k1.out[0], k2.in[0]);   // Internal buffer connection
connect<>(k2.out[0], out_C);
```

## Output Files

This sub-skill produces:

1. **`<kernel_name>_graph.h`** — Graph class definition with kernel instantiation and port connections
2. **`<kernel_name>_app.cpp`** — Application wrapper with PLIO/GMIO connections for simulation
3. **`aie.cfg`** — Compiler configuration (kernel-linting, xlopt, verbose, pl-freq, Xmapper)
4. **`Makefile`** — Build automation with hw, x86sim, aiesim, profile, and trace targets
5. **`<kernel_name>_app.aiecst`** — Constraints file (empty JSON initially)
6. **`data/`** — Directory structure for test data (populated by validate sub-skill)
