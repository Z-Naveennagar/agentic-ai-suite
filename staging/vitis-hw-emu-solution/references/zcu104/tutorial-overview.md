# Tutorial Overview

## Scope

Load this file when the user needs the high-level flow for the ZCU104 Edge AI platform-creation tutorial or when deciding whether a problem belongs here or in `the cosim runtime references (`references/cosim/`)`.

## Purpose

This skill covers the custom embedded platform creation flow for ZCU104 that precedes hardware emulation and co-simulation. The tutorial’s structure is stage-oriented:

1. create the hardware platform in Vivado
2. assemble the software platform and bootable Linux-facing artifacts
3. validate the resulting platform with an application
4. iterate efficiently when hardware or software content changes

Treat the platform as a prerequisite for later `hw_emu` and cosim work.

## Target Platform

| Property | Value |
|----------|-------|
| Board | ZCU104 Evaluation Board |
| SoC | Zynq UltraScale+ MPSoC |
| Part | xczu7ev-ffvc1156-2-e |
| Linux CPU | Cortex-A53 (`psu_cortexa53`) |
| QEMU instances in hw_emu | 1 (APU only) |
| AI Engine | No |
| Memory | DDR4 (single NOC) |

## Tutorial-Specific Names

The 2025.2 tutorial consistently uses these names and paths:

- workspace root: `WorkSpace`
- step-1 hardware folder: `WorkSpace/zcu104_hardware_platform`
- Vivado project name: `zcu104_custom_platform`
- exported hardware XSA: `zcu104_custom_platform_hw.xsa`
- exported hardware-emulation XSA: `zcu104_custom_platform_hwemu.xsa`
- common image archive: `xilinx-zynqmp-common-v2025.2.tar.gz`
- extracted common image directory: `xilinx-zynqmp-common-v2025.2`
- platform component name in Vitis: `zcu104_custom`
- platform output path: `workspace/zcu104_custom/export/zcu104_custom/`
- generated DTB location: `<platform component>/hw/sdt/system.dtb`

The stage ordering is unchanged in 2025.2:
- create the hardware and export the XSA
- prepare the common image and build the Vitis platform
- validate the platform with `platforminfo` and a vector-add application

The major Step 2 change is how the DTB is produced:
- the default tutorial path no longer uses a separate `createdts` run
- `system.dtb` is generated by the Platform Wizard during platform creation
- treat standalone `createdts` guidance as legacy, not as the default flow

Use these exact names when mapping a user’s state against the tutorial. If their names differ, translate explicitly rather than assuming their layout is wrong.

## Known 2025.2 Differences vs Earlier Versions

| Item | 2024.1 and earlier | 2025.2 |
|------|-------------------|--------|
| DTB generation | `createdts` via `xsct` | Platform Wizard auto-gen from XSA SDT |
| vadd source location | `$XILINX_VITIS/examples/vadd/` | `$XILINX_VITIS/samples/vadd/` |
| PLATFORM default in step3 | Correct | Missing `ws/` prefix — pass explicitly |
| FSBL/PMUFW | Required as inputs | Auto-generated by platform build |

## Boundaries

Stay in this skill when the user is:
- building or reviewing the platform hardware
- exporting or replacing the XSA
- assembling boot components, DTB, kernel, rootfs, or sysroot inputs
- building or checking the `.xpfm`
- validating the platform build with `platforminfo` or a sample application

Switch to `the cosim runtime references (`references/cosim/`)` when the user is:
- launching `hw_emu`
- debugging QEMU or simulator startup
- diagnosing PS/PL traffic, DTB cosim overlays, remote-port, or DDR-sharing issues

## Expected Artifact Chain

Think in this order:

1. Vivado design and exported XSA:
   - `zcu104_custom_platform_hw.xsa`
   - optionally `zcu104_custom_platform_hwemu.xsa`
2. boot and Linux software inputs:
   - `bl31.elf`
   - `u-boot.elf`
   - `boot.scr`
   - `Image`
   - `rootfs.ext4`
   - installed `sysroot`
   - generated `system.dtb`
   - generated `fsbl.elf` and `pmufw.elf`
3. generated platform package and metadata:
   - `zcu104_custom.xpfm`
   - `vitis-comp.json`
   - boot folder contents
4. application build and validation output:
   - `platforminfo` output
   - `sd_card.img`
   - vector-add host and xclbin artifacts

If any earlier stage is incomplete, later failures are usually downstream symptoms.

## Fast Path Commands

The tutorial also exposes command-line fast paths:

```bash
cd step1_vivado
make all

cd step2_pfm
make all COMMON_IMAGE_ZYNQMP=<path/to/common_image/>

cd step3_validate
make all
```

There is also a top-level `ref_files` flow for building through validation, plus a `make sd_card` target for generating the SD-card image. Use the fast-track commands only when the user wants to follow the tutorial’s scripted path rather than the GUI path.

## Scripted Makefile Flow

The `ref_files/Makefile` is the orchestration entry point for the scripted flow.

The key top-level targets are:
- `make all COMMON_IMAGE_ZYNQMP=<path>`:
  - verifies `COMMON_IMAGE_ZYNQMP/Image` exists
  - runs Step 1 to generate the XSA
  - runs Step 2 to generate the platform
  - runs Step 3 with `TARGET=hw_emu`
- `make sd_card COMMON_IMAGE_ZYNQMP=<path>`:
  - verifies the common image
  - runs Step 1 and Step 2
  - runs Step 3 with `TARGET=hw`

The scripted dependency chain is:
- XSA target: `step1_vivado/build/vivado/zcu104_custom_platform_hw.xsa`
- platform target variable: `step2_pfm/zcu104_custom/export/zcu104_custom/zcu104_custom.xpfm`
- validation handoff: `make run TARGET=hw_emu -C step3_validate` or `make sd_card TARGET=hw -C step3_validate`

When answering scripted-flow questions, distinguish:
- the tutorial’s conceptual stage ordering
- the exact Makefile implementation used by `ref_files`

The official Makefiles also contain some legacy residue:
- the top-level XPFM variable still points to `step2_pfm/zcu104_custom/export/...`
- the Step 3 Makefile defaults `PLATFORM` to `../step2_pfm/ws/...`

Treat the Step 3 `PLATFORM` path as the more operationally important reference for the scripted flow.
