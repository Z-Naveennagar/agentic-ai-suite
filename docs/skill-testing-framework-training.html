Why this exists

Skills used to ship on faith

Before this framework, "does my change still work?" had one answer: try it by hand, once, and hope.

Without a harness

  • One manual run, one client, one model — if it happened to work that time
  • No record of what "working" even looked like last week
  • A prompt tweak that quietly breaks another skill's trigger goes unnoticed
  • Regressions surface in someone else's session, days later
  • Promoting a skill to production is a guess, not a decision

What we actually need

  • Run the same case repeatedly, across the clients customers actually use
  • A durable, inspectable record of pass/fail — not a memory
  • A structural check before anything ever executes an LLM
  • The same validation to run identically on your laptop and in CI
  • Evidence, not a guess, behind every staging → production promotion

The framework

skills-test: run, grade, benchmark

One harness that launches an agent CLI against a test case, captures what it did, grades the result, and remembers it.

✍️
You author
a skill in staging/ + a test suite in tests/
→
🚀

Claude Code, Cursor, Copilot, or opencode — your call
→
📋

artifacts, content, metrics, LLM judges — automatic
→
🗄️
Recorded
every run written to SQLite — nothing is forgotten
→
📊
Reported
a dashboard + a per-skill signoff you can hand to a reviewer

Two trees, one install

staging/<skill>/SKILL.md (what the skill is) and tests/<skill>/<suite>/ (how you prove it works) are separate, authored trees. skills-test install validates and joins them — only a skill with a passing suite ever reaches .claude/skills/ or .opencode/skills/.

Getting started

Three files. That's the whole contract.

Scaffold a canonical suite in one command — then just fill in what you'd write anyway.

# scaffold a suite for your skill
skills-test init --skill my-skill --suite my-suite

# creates tests/my-skill/my-suite/
tests/my-skill/my-suite/
├── runner_spec.yaml   # clients, timeouts, requirements
├── grader_spec.yaml   # how a case is scored
├── test_cases.yaml    # the prompts + expected values
└── inputs/            # files staged into the workspace

runner_spec.yaml

Which client(s)/model(s) to run against, Vivado/Vitis requirements, timeout, retries.

grader_spec.yaml

One shared scoring rubric — artifact checks, content matches, metric thresholds, even an LLM judge.

test_cases.yaml

The list of prompts and expected values every case in the suite substitutes in.

grader_spec.yaml, in depth

Graders: what actually gets checked

Every case is scored by one or more graders — pick the kind that matches what "correct" means for your skill.

GraderWhat it checksUse it when…
artifact_existsA file exists at a path and is at least N bytesThe skill should produce a specific output file
artifact_validA file exists and passes a named validator (e.g. is a real Vivado DCP)Existence alone isn't proof — the file has to be structurally correct
content_containsA substring/regex is present (or absent) in stdout/stderr/a fileSimple text evidence — a keyword, an absence of "ERROR:"
metric_thresholdA numeric value clears a threshold (>=, <, …)"Achieved FPS must be ≥ target"
metric_delta / baseline_deltaA metric vs. a stored baseline — directional (must improve) or symmetric (within tolerance)QoR impact: did this change help, hurt, or hold steady?
oracle_matchExtracted values against a hand-curated oracle (required items present, forbidden ones absent)Classification / triage skills with a known-correct answer set
artifact_signatureThe artifact carries headers a tool actually emits — defeats "fake it with a heredoc"You need proof the real tool ran, not a plausible-looking fabrication
tool_call_observedAn external tool was actually invoked (filesystem side-effect or transcript command)The skill's whole point is triggering a specific tool call
action_sequenceThe agent's tool-call sequence matches an expected order/setProcess matters, not just the end state (read → skill → compile)
triggerDid the skill activate at all? (probability from the transcript)Testing whether a skill fires on the prompts it should (and doesn't on ones it shouldn't)
llm_judgeAn LLM scores the answer against a rubric (0–100)The correct answer is judgment-based prose, not something a regex can check
diff / config_matchExpected file edits, or a tolerant JSON-config comparisonCode-editing skills; skills that produce a structured config
Families expand into several graders violation: → verdict + rule-citation checks tool-execution: → trigger + sequence + tool-call checks

How a suite actually runs

Two lifecycles: per-run setup, and consistency over time

A suite has a fixture lifecycle around each shared run, and every skill has a longer-running consistency lifecycle across runs.

Per-run: setup / reset / teardown

1
setup
once per (suite, client, model) group — start a shared session
2
reset
after every case except the last — restore shared state; a failure here is fatal to the whole group
3
teardown
once, after the group's last case — wipe the shared workspace

Prefer kind: python/bash over prompt: a prompt-based setup makes one LLM turn the gate for every case — when it improvises, the failure looks like a skill failure. Direct scripts don't add LLM variance.

Across runs: the consistency lifecycle

Every skill moves through a state machine driven by repeated runs, not a single verdict:

UNASSESSED KEEP WATCH DEPRECATE REMOVE
  • Below min_reps (default 3) or full coverage → UNASSESSED, never a weak verdict
  • Passing gates → KEEP; a failing run moves a healthy skill to WATCH
  • Two consecutive failures → DEPRECATE; sustained failure → REMOVE
  • Gates check pass rate, per-case score spread, and mandatory/weighted grader failures

The daily loop

Four commands cover the whole workflow

The same commands you run on your laptop are what CI runs — no separate "CI-only" path to trust blindly.

# 1. is my host ready?
skills-test doctor

# 2. validate + install (dry run first)
skills-test install --dry-run
skills-test install

# 3. see what's discoverable
skills-test list --tags smoke

# 4. run it — validate the plan first
skills-test run --skills my-skill --dry-run
skills-test run --skills my-skill --reps 3

--dry-run everywhere

Validates manifests and prints the exact execution plan — zero LLM calls, zero cost, catches a typo before it costs you tokens.

--reps N

Repeats each case within one run record, so consistency (not just a single lucky pass) is what gets measured.

--client / --model

Force a one-off backend for this invocation — outranks everything else, no suite file edits needed.

"Installed" and "works" are different questions

doctor doesn't just check a binary exists — it runs it, and it sends a real prompt through.

Presence check alone (the old way)

[PASS] cli_cursor: /usr/local/bin/agent

Looked healthy. In reality this install was missing its own runtime — every real invocation failed instantly.

Functional check (today)

[FAIL] cli_cursor: /usr/local/bin/agent

Set expectations honestly

What's free, and what you actually have to write

skills-test init gives you a skeleton — the judgment calls are still yours.

FileScaffold gives youYou still author
runner_spec.yamlMostly usable: client/model, defaults, tags: [smoke]Real timeout, Vivado/Vitis flags, and — for shared sessions — setup/reset/teardown
grader_spec.yamlOne placeholder grader (response_not_empty)The real rubric — every field, every grader, weights and mandatory flags
test_cases.yamlOne empty-prompt stub caseReal prompts, staged input files, golden expected values
inputs/An empty directoryEvery file the prompt references

Bottom line

Of the three files, only runner_spec.yaml is substantially reusable out of the box. Plan real authoring time for the grading rubric and the test cases — that's where your skill's actual correctness bar lives.

Minimum bar to ship

  • ≥1 structurally-valid suite to pass skills-test install
  • 3 reps, full coverage, to get a real lifecycle signoff (not UNASSESSED)
  • Skill must be in config.yaml's allowlist to be run at all

The payoff

What this framework gives you back

  • ✓
    Confidence to change things. A prompt tweak, a new grader, a model swap — run the suite, see the delta, ship or don't.
  • ✓
    Consistency, not luck. --reps 3+ catches the skill that passes sometimes and fails other times — the failure mode a single manual try can never see.
  • ✓
    Cross-client coverage for free. One suite, four backends (Claude Code, Cursor, Copilot, opencode) — write once, validate everywhere your customers actually work.
  • ✓
    A durable signoff package. Every run writes a per-skill report — the evidence a reviewer needs to approve staging → production, not a verbal "trust me."
  • ✓
    Fast, cheap failure. --dry-run and structural validation catch a typo before a single LLM token is spent.
  • ✓
    Nothing silently breaks. A skill with no suite is flagged; a skill with a real problem fails loudly, with a reason.
  • ✓
    The same commands everywhere. What you run locally is exactly what CI runs — no surprises from an untested "CI-only" path.
  • ✓
    A dashboard, not a memory. Every result lands in SQLite — pass rates, score trends, cost — queryable, not folklore.
